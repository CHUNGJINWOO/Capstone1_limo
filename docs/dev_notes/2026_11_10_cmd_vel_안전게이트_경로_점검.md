# 2026-11-10 cmd_vel 안전 게이트 경로 점검

## 목적

모든 모터 명령이 `stall_detector_node`(안전 게이트)를 거쳐 `/cmd_vel`에 도달하는지 점검했다. 기동 직후 FAILSAFE가 고정되는 문제도 함께 다뤘다. 시뮬레이션 launch 2개와 공용 게이트 코드는 수정했고, 실차 launch는 **문서화만** 하고 수정하지 않았다.

## 수정한 것 (시뮬레이션 + 공용 게이트)

| 파일 | 변경 |
|---|---|
| `limo_capstone/stall_detector_node.py` | `INITIALIZING` 상태 추가. 기동할 때와 `reset_latch` 후에는 출력을 0으로 유지하다가, 필요한 입력이 `startup_ready_hold_sec`(0.5 s) 동안 정상이고 명령이 0일 때만 NORMAL로 넘어간다. `startup_timeout_sec`(30 s) 안에 넘어가지 못하면 FAILSAFE. INIT 중 reset은 거부한다. 파라미터 `require_wheel_odom`(기본 True)와 `estimator_odom_topic`(기본 '')을 추가했다 |
| `launch/limo_integrated_auto_mapping_sim.launch.py` (Ackermann) | Nav2 remap을 `cmd_vel_smoothed→/cmd_vel_raw`, `behavior_server:cmd_vel→/cmd_vel_raw`로 바꿨다. 게이트에 `estimator_odom_topic: /odom_nav2`를 넘긴다 |
| `launch/limo_integrated_auto_mapping_sim_diff.launch.py` | 위와 동일 |

기동 FAILSAFE의 원인: `depth_obstacle_filter`는 points를 먼저 publish하고, status는 별도의 20 Hz 타이머로 보낸다. 첫 points가 온 뒤 첫 `ready` status가 오기까지 최대 50 ms 동안 게이트는 `depth_invalid`로 판단하고, `require_operator_unlatch=True` 때문에 이 상태가 영구히 고정됐다. 실측 간격은 약 30 ms였다.

이전 시뮬레이션 우회 문제: 전역 `SetRemap(cmd_vel→/cmd_vel_raw)`가 노드별 remap보다 먼저 적용된다. 그 결과 `velocity_smoother`는 `/cmd_vel_raw`를 입력으로 받고 출력 `cmd_vel_smoothed→cmd_vel`을 그대로 `/cmd_vel`로 내보내 게이트를 우회했다. Ackermann에서는 FAILSAFE 중 로봇이 약 9 cm 이동하는 것으로 재현됐다.

## 추정기별 입력 의존성 (real launch 기준, 코드에서 확인)

| 추정기 | 추정 입력 | 출력 → relay | 게이트가 요구하는 것 |
|---|---|---|---|
| B0 | `/odom` | `/odom` → `/odom_nav2` | scan, wheel odom, (ICP observer가 켜져 있으면) lidar odom/ICP, depth(depth_mode) |
| F1b | `/odom` + `/imu` (EKF) | `/odometry/ekf_tuned` | 위와 동일 |
| F3b | `/odom` + `/imu` + `/scan` | `/odometry/comp_slip_gate` | 위와 동일 |
| F4 | `/scan` (ICP) | `/odometry/lidar_odom` | scan, lidar odom, ICP, wheel odom, depth |
| F5_improved | lidar odom + `/imu` (EKF) | `/odometry/f5_improved` | F4와 동일 |

- lidar odom과 ICP는 `require_lidar_odom`이 True일 때만 요구한다. real launch는 `run_icp_observer` 값이나 f4/f5 선택에 따라 이 값을 정한다.
- depth는 `depth_mode`(required/optional/disabled)를 따른다. real launch는 `use_depth_camera=false`이면 `disabled`로 넘긴다.
- `estimator_odom_topic`은 시뮬레이션 launch에서만 `/odom_nav2`로 지정했다. 추정기가 무엇이든 relay 출력은 이 토픽 하나라서 추정기별 분기가 필요 없다.

## 실차 launch(`limo_integrated_auto_mapping_real.launch.py`) — 수정함 (11-10 2차)

수정 전 문제(정적 분석):
1. `enable_stall_detector` 기본값 false에서 `allow_motor_drive:=true`를 주면 Nav2 명령이 gate 없이 `/cmd_vel`(모터)로 직접 나갔다.
2. 전역 `SetRemap(cmd_vel / cmd_vel_smoothed → 같은 목적지)` 때문에 velocity_smoother가 자기 출력을 다시 입력으로 받았다. 전역 remap이 노드별 remap보다 먼저 적용되기 때문이다.

수정 내용:
- Nav2 명령은 항상 `/cmd_vel_raw`로 보낸다. `cmd_vel_smoothed → /cmd_vel_raw`, `behavior_server:cmd_vel → /cmd_vel_raw`. 전역 `cmd_vel` remap은 제거했다. controller → `cmd_vel_nav` → smoother → `/cmd_vel_raw` 경로는 Nav2 기본 배선이다.
- stall gate는 항상 정확히 하나만 실행한다(`stall_detector_node`). 출력 토픽은 `allow_motor_drive`가 정확히 문자열 `true`일 때만 `/cmd_vel`, 그 외(`false`, `TRUE`, 빈 값)는 모두 `/cmd_vel_locked`다. 기존의 live/locked 노드 2개 구성은 하나로 합쳤다.
- `enable_stall_detector`는 기존 스크립트(`auto_mapping_experiment_manager.py` 등)가 넘기므로 인자는 남기되 **무시**한다(기본 true, false를 주면 DEPRECATED 로그).
- gate에 `estimator_odom_topic: /odom_nav2`를 전달한다.
- Ackermann 복구 BT를 적용한다(아래 "Ackermann 복구" 참고).
- 추정기와 Depth on/off 선택 로직(`estimator_type`, `run_icp_observer`, `use_depth_camera`, `depth_mode`)은 그대로다.

잠금 모드에서 `/cmd_vel` 소비자는 `limo_base`뿐이고 발행자는 없다. 모터 구동은 시험하지 않았다.

## 주행 중 odometry 감시 (`stall_detector_node.py`)

- 대상: wheel `/odom`(`require_wheel_odom`, 기본 True)과 `estimator_odom_topic`(미설정이면 감시 안 함). 한도는 `odom_timeout_sec`(기본 0 → `sensor_timeout_sec`).
- 판정은 scan/lidar와 같은 규칙이다. 한 번이라도 수신하던 스트림이 끊기면 stale, 한 번도 수신하지 못한 스트림은 명령이 들어올 때만 stale로 본다.
- INITIALIZING 중에는 이 판정을 쓰지 않고 arm 조건(`checks`)만 본다. 그래서 초기화 중 미수신과 주행 중 단절이 구분된다. 단절되면 `FAILSAFE_SENSOR_TIMEOUT`, 로그와 status JSON에 `wheel_odom_stale`, `est_odom_stale`이 남는다.
- 추정기별 의존성: 감시 대상은 launch가 넘기는 파라미터로만 정해진다. B0/F1b/F3b는 lidar odom·ICP·depth를 요구하지 않고(`require_lidar_odom`, `depth_mode` 값에 따름), 모든 추정기가 `/odom`과 `/odom_nav2`를 요구한다.
- 같이 고친 결함: `require_operator_unlatch=False`(실차 설정)에서 startup timeout으로 들어간 FAILSAFE가, 센서가 한 번도 오지 않았는데도 "stale 아님"으로 판단되어 곧바로 NORMAL로 돌아왔다. FAILSAFE 자동 복구 조건에 "필요한 모든 입력이 실제로 fresh"를 추가했다.

## Ackermann 복구 (Spin 제거)

- 원인: Nav2 기본 BT(`navigate_to_pose_w_replanning_and_recovery.xml`)의 복구 단계에 `Spin`이 있다. Ackermann 모델은 angular 명령만으로 회전하지 못해 시험에서 yaw 변화가 0°였고 Spin이 시간 초과했다. `BackUp`도 gate가 후진을 막고 있어(`enable_auto_reverse=false`, 후방 센서 없음) 이동하지 못한다.
- 수정: `config/navigate_to_pose_ackermann_no_reverse.xml` 새 파일(복구 = costmap 지우기 + 대기, Spin/BackUp 없음). 팀의 `navigate_to_pose_ackermann.xml`은 BackUp이 있어 그대로 두었다.
- 연결: `integrated_nav2_params.yaml`과 `integrated_nav2_lidar_only_params.yaml`에 `default_nav_to_pose_bt_xml` 자리 키를 추가했다. 값은 Nav2 기본 트리 경로라 직접 쓰면 기존과 동일하다. Ackermann sim launch와 real launch가 `RewrittenYaml`로 이 키를 새 BT 경로로 바꿔서 쓴다. Differential 설정·launch는 변경하지 않았다.

## 실차 적용 전 필요한 검증

- 모터 잠금 상태(`allow_motor_drive=false`)에서 `ros2 topic info -v /cmd_vel`로 publisher가 게이트 하나인지 확인
- 각 추정기(B0/F1b/F3b/F4/F5)와 depth 사용 여부 조합에서 INITIALIZING → NORMAL 전환 시간, 그리고 timeout 사유 로그(`not_ready=[...]`) 확인
- 실제 센서 주기에서 `sensor_timeout_sec` 0.38 s의 여유 확인 (실차 RTF/지연)
- 바퀴를 띄운 상태에서 scan/lidar odom/depth/wheel odom을 하나씩 끊어 FAILSAFE와 모터 0 출력 확인
- MCU watchdog와 물리 E-Stop 동작 (소프트웨어 게이트와 별개)
- smoother 파라미터 정의 (현재 yaml에 없어 기본값 사용: accel 2.5 m/s², OPEN_LOOP). 게이트가 막고 있을 때 smoother 상태가 실제와 어긋나는 문제는 `CLOSED_LOOP`으로 해결할지 검토

## 2차 시험 결과 (11-10)

- gate 단독(가짜 센서): 86/86 통과. 1차 49개 회귀 + 주행 중 wheel `/odom`·`/odom_nav2` 단절(F4/F5 구성, B0/F1b/F3b 구성), 실차 설정(`require_operator_unlatch=False`)의 startup timeout 유지와 런타임 복구, 유휴 중 단절, `estimator_odom_topic` 미설정 시 동작.
- real launch 잠금 모드(하드웨어 없음, `/dev/ttylimo` 없음): `/cmd_vel` 발행자 0·구독자 0, `/cmd_vel_locked` 발행자 gate 1개, `/cmd_vel_raw` 발행자 behavior_server ×3 + velocity_smoother, `bt_navigator`가 `navigate_to_pose_ackermann_no_reverse.xml` 사용. `allow_motor_drive`와 `enable_stall_detector` 조합 6가지는 launch 인자 평가로만 확인(gate 1개, 출력 토픽 `true`일 때만 `/cmd_vel`).
- 전체 sim: Ackermann은 `est_odom` 단절 → FAILSAFE·이동 0.0000 m, Differential은 `wheel_odom` 단절 → FAILSAFE·이동 0.0000 m. 두 launch 모두 `/cmd_vel` 발행자는 gate 하나, 단절된 소스가 죽은 채로 reset하면 INITIALIZING에 머문다. Differential은 기존 Nav2 기본 BT를 그대로 사용함을 확인했다.
