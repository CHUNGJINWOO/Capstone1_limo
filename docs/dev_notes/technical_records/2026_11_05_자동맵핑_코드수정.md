## 저속 YAML 변경값

| 설정 | 기존 | 저속 시험값 | 이유 |
|---|---:|---:|---|
| controller_server / FollowPath / max_vel_x | 0.26 | 0.10 m/s | 선속도 상한 저감 |
| controller_server / FollowPath / max_speed_xy | 0.26 | 0.10 m/s | DWB 평면 속도 상한 일치 |
| controller_server / FollowPath / max_vel_theta | 1.0 | 0.4 rad/s | 경로 추종 중 회전 상한 저감 |
| controller_server / FollowPath / trans_stopped_velocity | 0.25 | 0.02 m/s | 목표 근처 RotateToGoal의 정지 판단 임계값이 저속 상한보다 높은 문제 방지 |
| behavior_server / max_rotational_vel | 1.0 | 0.4 rad/s | 회전 복구 상한 일치 |
| behavior_server / min_rotational_vel | 0.4 | 0.1 rad/s | 복구 회전의 최소 속도도 낮춤 |
| velocity_smoother / max_velocity | [0.26, 0, 1.0] | [0.10, 0, 0.4] | smoother의 명령 상한 일치 |
| velocity_smoother / min_velocity | [-0.26, 0, -1.0] | [-0.10, 0, -0.4] | 반대 방향 명령도 대응 |

이 값은 비교 시험의 시작값이며 실물 안전 보장값이 아니다. footprint, robot_radius, inflation, 목표 허용 오차, 가속·감속, 진행 감시 조건은 그대로 유지했다. 로봇의 최신 설정과 복사 기준이 달라졌을 수 있으므로 현장에서 비교해야 한다.

속도 저감의 범위는 DWB 경로 추종, smoother 설정, 회전 복구 설정이다. teleop·다른 cmd_vel 발행자 또는 모든 행동의 속도를 강제하는 독립 안전 제한기는 추가하지 않았다. 특히 현재 Humble navigation_launch.py에서는 behavior_server 출력이 controller와 동일한 smoother remapping을 거치지 않는 구성이므로, 실제 cmd_vel과 복구 동작도 확인해야 한다.

정지 판단 임계값 근거: [Nav2 Humble RotateToGoal 소스](https://api.nav2.org/nav2-humble/html/rotate__to__goal_8cpp_source.html). 속도 상한 근거: [Nav2 Humble DWB 소스](https://api.nav2.org/nav2-humble/html/kinematic__parameters_8cpp_source.html), [Nav2 Humble velocity smoother 소스](https://api.nav2.org/nav2-humble/html/velocity__smoother_8cpp_source.html). 소스의 기능을 참고해 선택한 수치이며, 0.10·0.4·0.02·0.1 자체가 공식 권장값인 것은 아니다.

## 오류·목표 기록을 읽는 방법

- INPUT_MISSING: 해당 토픽 미수신.
- INPUT_STALE: 마지막 수신 후 경과 시간이 제한을 넘음.
- STAMP_OUT_OF_RANGE: 메시지 timestamp가 오래됐거나 허용 범위보다 미래임.
- SCAN_INVALID: 측정 범위 내 유한한 스캔값이 없음.
- ROBOT_TF_UNAVAILABLE: 지도 기준 로봇 위치 조회 또는 기존 TF 신선도 검사 실패.
- SCAN_TF_UNAVAILABLE: 스캔 측정 시각의 센서→지도 TF 조회 실패. 프레임·시각·예외를 기록.
- FRAME_MISMATCH: 지도와 costmap frame 불일치.
- INPUTS_READY: 이전 준비 실패 이후 전체 검사 통과.

동일 원인의 준비 대기 경고는 2초 간격으로 제한하지만 마지막 실패 사유는 매 검사마다 갱신한다. 기존 5초 데이터 제한, -0.5초 미래 허용, 즉시 탐색 중단 정책을 늘리거나 완화하지 않았다. 동시에 여러 항목이 실패하면 검사 순서상 첫 실패를 기록한다. 단일 오류를 근본 원인으로 단정하면 안 된다.

EXPLORE_EVENT는 실제 코드 실행 시 관측한 값을 JSON으로 출력한다. goal_id는 explorer 내부 순번이며 Nav2 UUID가 아니다. 프로세스·회차와 로그 시각을 함께 사용한다. displacement_m은 누적 이동 거리가 아닌 시작점 대비 변위다. 위치 조회 실패는 null과 pose_error로 기록한다. 실제 지도 면적 증가나 물리 접촉을 자동 측정하는 기능은 이번에 추가하지 않았다.

## 검사 결과와 한계

- 노트북 colcon 빌드: 완료. 최종 설치본 검사 기록은 `records/verification.json`.
- 실제 함수·launch 구성·YAML 비교 및 기존 회귀: 최종 43개 통과.
- 기존 26개 검사에 새 검사 17개를 추가했다. 기존 검사 복사본의 Backend에는 새 오류 로그 호출을 수용하는 logger 시험 대역만 추가했다.
- 새 검사는 실제 ready(), until(), on_result(), execute(), launch start() 메서드를 호출한다. 센서·TF·Nav2 응답은 주입값/시험 대역으로 제공한다. Gazebo 주행·실물 시험으로 해석하지 않는다.
- 첫 검사에서는 시험용 timestamp를 ROS Time이 아닌 객체로 만든 문제와 sandbox 로그 경로 문제로 5개가 실패했다. ROS Time 메시지 사용 및 로그 경로 지정으로 시험 환경을 고친 뒤 최종 통과했다. 최초 XML도 보존했다.
- 정적 검사: Python flake8 F 검사 통과.
- 설치 launch의 --show-args: 새 인자와 기본값 확인.
- 새 Gazebo 주행, 실제 cmd_vel 상한, 실물 감속·정지 거리, 접촉 방지, 자동 위치 추정 통합: **미검증**.

유리·보강대 인식 알고리즘은 추가하지 않았다. 제자리 성공은 기존의 실패 횟수 미증가·쿨다운 정책을 유지하며 반복 상황의 완전한 해결을 주장하지 않는다. 목표 허용 오차와 탐색 완료 판정 기준을 임의로 줄이거나 바꾸지 않았다. 낮은 속도가 Nav2 progress checker에 미치는 영향은 비교 주행으로 확인해야 한다.
