### 2.1 책상 구조와 위험의 의미

책상은 다리 사이에 세로·가로 연결 보강대가 있는 구조이며, 의자도 주변에 배치돼 있다. RViz 화면에는 책상 아래로 지나는 경로가 표시됐다.

이 구간을 단순히 “물리적으로 통행 불가능”이라고 판단하지 않는다. **로봇이 통과할 수는 있지만 차체가 스치고, 책상·의자 배치에 따라 충돌 위험이 높은 구간**이다. 긁힘과 장비 손상 우려가 보고됐으며, 실제 손상 발생 여부와 접촉 부위·간격은 계측하지 않았다.

가능한 원인은 다음 두 가지로 나누어 확인해야 한다.

- LiDAR 스캔 평면이 보강대 위·아래를 지나 다리는 관측해도 접촉하는 연결 구조는 관측하지 못함.
- 구조물은 관측되지만 costmap 반영, 로봇 차체·돌출부 footprint, 여유 간격이 충분하지 않음.

현재 화면만으로 두 경우 중 하나를 확정할 수 없다. 또한 책상 아래를 수동으로 피해 주행했다고 그 공간이 자동으로 통행 금지 처리되는 것은 아니다.

### 2.2 목표 도달 및 탐색 종료는 구분 필요

장애물이 가까우면 목표 도달로 처리된다는 해석은 아직 가설이다. 후속 시험에서는 다음을 구분한다.

1. 가까운 개별 목표가 Nav2 허용 오차 안에 있어 이동 없이 `SUCCEEDED`가 반환됨.
2. 목표 실패·제외 목록 때문에 남은 후보가 소진됨.
3. 실제 미탐색 경계가 없어 전체 탐색이 완료됨.

이전 C++ middle 시험에서 보고된 조기 종료·블랙리스트 소진·취소 후 정지 현상과, 오늘 Python 수정본의 동작을 같은 결과로 취급하지 않는다. 수정본이 이 문제를 실물에서 해결했는지는 아직 확정하지 못했다.

## 3. 자동 맵핑 중단 결과와 로그 조사

### 3.1 Action 결과

```text
elapsed_sec: 약 175.18
retry_count: 0
success: false
exploration_complete: false
margin_retried: false
message: Sensor/map/costmap/TF health lost; stopping exploration
posegraph_prefix: ''
Goal finished with status: ABORTED
```

이 결과는 충돌 센서가 유리 충돌을 검출했다는 뜻이 아니다. 또한 시간 제한으로 종료했다는 메시지도 아니다. 코드의 상태 검사 실패를 상위 Action이 보고한 것이다.

확인한 `server.py`에서는 지도·global costmap·스캔의 수신 및 timestamp, 유효 스캔값, 필요한 TF 조회, 지도·costmap frame 일치 등을 검사한다. 데이터 제한 기본값은 5초다. 현재 구현은 여러 실패 원인을 같은 메시지로 합쳐 반환하므로 이번 실행에서 어느 검사가 실패했는지는 알 수 없다.

### 3.2 로그에서 확인한 사실

이번 맵핑 launch는 16:19:33에 시작됐고, 마지막에는 사용자의 Ctrl+C로 종료됐다. launch 로그의 `finished cleanly`는 프로세스 종료 상태이며 탐색 성공을 뜻하지 않는다.

| 시점·자료 | 확인된 내용 | 해석의 한계 |
|---|---|---|
| 초기 planner 로그 | map TF가 아직 없다는 메시지 이후 costmap 시작 | 초기 준비 구간 오류만으로 중간 종료 원인을 판단할 수 없음 |
| 약 16:23:14~16 | 목표 `(0.32, -10.58)` 경로 계획 실패, costmap 초기화·재계획 반복 | 실패 목표가 실제 유리 내부인지 좌표만으로 확정하지 못함 |
| 같은 시기 및 이후 | laser_link 메시지가 TF 캐시보다 오래됐다는 이유로 폐기됨 | TF 시각 처리 문제의 증거. 충돌과의 인과관계는 미확정 |
| SLAM 로그 마지막 약 16:38~16:41 | `discarding message because the queue is full` 반복 | 스캔 필터 대기열 포화·폐기 확인. CPU 부족으로 단정할 수 없으며 중단 시점보다 뒤의 기록임 |
| 이번 mapping server 로그 | 해당 Python 로그 파일 내용이 비어 있음 | Action의 세부 실패 원인이 로그에 남아 있지 않음 |

조사 시 하루 전체 로그가 섞였으므로 다음 내용은 이번 충돌의 직접 근거에서 제외했다.

- 이전 16:09~16:13 실행의 반복 TF 오류.
- 16:12:04의 `/dev/ttylimo` 열기 실패: 별도 실행에서 확인됐으나 이번 실행 원인으로 연결하지 않음.
- 다른 날짜 YDLIDAR 로그의 QoS 경고: PID·timestamp 문자열 검색에 섞인 과거 자료.

`~/.ros/log/latest` 링크는 해당 LIMO 환경에 없었다. 여러 파일에서 grep한 결과에 `tail`을 적용해도 시간순 최신 오류라는 뜻은 아니므로, 실행 시각과 정확한 파일명을 대조했다.

- 파일 목록: `C103_11_05.yaml`, `.pgm`, `.posegraph`, `.data` 생성 확인.

이후 같은 경로로 불러올 때 YAML 및 posegraph/data가 없다는 오류도 발생했다. 파일 이동·현재 경로가 대화에서 최종 대조되지는 않았으므로 “현재도 해당 경로에 존재한다”고 보장하지 않는다. 다시 사용할 때 실제 위치와 YAML의 이미지 경로를 확인해야 한다.

### 4.2 위치 저장과 재위치 추정

처음 `tf2_echo map base_link`로 위치를 저장할 때는 map과 base_link가 연결되지 않았다는 오류가 나왔다. 당시 `_pose.txt`는 좌표가 아니라 오류 로그이므로 시작 위치로 사용할 수 없다.

이후 별도 실행에서 다음 TF 값은 출력됐다.

```text
x = -0.055 m
y =  0.114 m
yaw = 0.026 rad
```

좌표 출력 자체가 위치 정확도를 검증한 것은 아니다. 해당 저장 지도를 사용하고 RViz의 스캔·벽 정합을 확인했는지, 로봇이 이후 이동했는지에 따라 재사용 가능 여부가 달라진다. 고정 시작 좌표로 일반화하지 않는다.

현재 수동 이어 맵핑은 저장 지도와 AMCL에서 2D Pose Estimate로 위치를 잡고, 확인한 좌표를 SLAM 이어 맵핑의 `start_pose`에 전달하는 방식이다. AMCL과 SLAM을 중복 실행하지 않는다. 좌표 없는 자동 위치 추정 기능은 별도 개발·검증 항목이며 이번 두 파일 시험과 구분한다.

사용자는 이후 이어 맵핑 중 책상 아래 접촉을 보고했다. 다만 최종 지도 완성·자동 저장 성공까지 확인한 기록은 없다. 원본 지도는 보존하고 추가 작업 지도는 새 이름으로 저장한다.

### 4.3 Costmap 기록

global/local costmap 메시지와 파라미터를 별도로 저장하는 방법을 안내했다. **오늘 실제로 저장에 성공했다는 출력은 전달받지 못했다.**

Costmap은 당시 장애물·inflation 상태를 남기는 분석용 스냅샷이다. 지도 이미지·posegraph와 목적이 다르고 그대로 이어 맵핑 상태를 복구하는 파일이 아니다. 각각 따로 수신한 기록은 동일 시각 스냅샷으로 취급하지 않는다.

## 5. 개선 제안 — 아직 적용·검증하지 않은 내용

| 우선 항목 | 제안 | 효과 및 한계 |
|---|---|---|
| 상태 진단 | 실패 데이터 항목, 수신 경과 시간, timestamp 차이, TF frame·요청 시각·예외를 로그와 Action 결과에 기록 | 다음 중단의 원인을 특정하기 위한 변경. 유리 인식을 직접 해결하지는 않음 |
| 주행 속도 저감 | 자동 맵핑 시험용 선속도·회전속도를 낮춤. controller와 velocity smoother 설정을 함께 점검 | 늦은 반영에 대응할 시간과 충격 저감에 도움이 될 수 있음. 보이지 않는 구조물을 보이게 만들지는 않음 |
| 목표·진전 기록 | 목표 좌표, 전송·수락·취소·종료, 실제 변위·지도 변화, 제외 사유를 함께 기록 | 이동 없는 성공, 후보 소진, 탐색 완료를 구분 |
| Footprint·여유 간격 | 차체와 돌출부의 실제 외형 및 책상·의자 주변 여유 점검 | 관측된 장애물과의 접촉 방지에 필요. 미관측 보강대에는 한계가 있음 |
| 유리벽·유리문 대응 | 스캔 → costmap → 계획 경로를 대조하고 문 열림·닫힘 조건을 분리 | 알려진 위치의 통행 제한과 센서만으로 판단하는 시험을 구분. 필요 시 추가 센서·문 상태 인식 검토 |

이번 기록 작성에서는 주행 속도, 목표 허용 오차, 센서 설정, 안전마진 및 코드 동작을 추가로 수정하지 않았다. 속도 저감 효과나 유리문 인식 개선을 검증 완료로 표현하지 않는다.

## 6. 다음 작업 순서

1. 현재 코드·설정과 실물 로그를 보존하고, 실패 원인을 드러내는 진단 로그를 먼저 보강한다.
2. 기존 설정을 복사한 시험용 설정에서 속도를 낮춘다. 속도 저감에 따른 진행 감시 시간의 적절성도 확인한다.
3. 유리·접촉 위험 구조물을 피한 정상 구간에서 기존 속도와 저속 조건을 비교한다. 한 번에 다른 정책까지 변경하지 않는다.
4. 가까운 목표에서 Nav2 성공과 실제 이동을 대조하고, 실패 제외·후보 소진·완료 판정을 별도로 검증한다.
5. 책상 접촉 보강대가 스캔에 보이는지 확인한 뒤 footprint·여유 간격 또는 추가 관측·통행 제한을 선택한다.
6. 유리벽·유리문은 관측 조건별로 분리한다. 충돌을 반복해 확인하는 방식 대신 관측과 경로 판단부터 검증한다.

성공 기준은 단순히 경로가 생성되거나 로봇이 통과하는 것이 아니라, **실제 차체가 접촉 없이 필요한 여유를 확보해 주행하고, 진행·정지·종료 사유를 근거와 함께 확인할 수 있는 것**으로 둔다.
