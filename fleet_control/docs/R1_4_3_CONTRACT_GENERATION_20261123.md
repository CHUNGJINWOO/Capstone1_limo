## 1. Root cause (traced in the code)
`AgentCore.run` updates the contract fields from state reply N and then calls `_on_command` for the commands of that same reply. `_on_command` never looked at the contract: for `navigate_to_pose` it only parsed the command's own safety context, journaled `RECEIVED` and called `handler.start_navigate`, which just appends to `RosRobot.tasks`. The contract was evaluated only later, by `RosRobot._do_nav` (`verify_navigation_execution` -> `compute_movement_permitted`) on the ROS side, using whatever the session said at that moment. So (1) a motion command received in an invalid reply was queued as RECEIVED, and if reply N+1 restored the contract before the ROS thread ran `_do_nav`, the check saw a valid contract and submitted it (Codex: 1 submission); (2) the live-goal duty to cancel existed only as a pure function of the CURRENT session (`check_active_goal_safety`), evaluated by `_monitor_active_goal` on the 0.1 s timer; if the contract was valid again by the first monitor run, no fault was found and no cancel was requested (Codex: 0 cancels).

## 3. Generation and state transitions
`contract_generation` g: +1 whenever the Agent's contract goes from valid to invalid (invalid reply, missing/bad key, bad protocol, hello restart, boot change, `needs_reconcile`); it never decreases and never changes on recovery. A command is admitted only if valid at receipt and carries the g of that moment; it may run only if the session still has the same g at each execution stage. A goal carries the g it was submitted under; once the session g differs, `check_active_goal_safety` reports `SERVER_CONTRACT_INVALID` on every monitor run, so the cancel duty cannot be erased by a recovery (the record is dropped only when the goal ends; a new goal gets the then-current g). The cancel is requested by the existing monitor logic (request flag set once, no repeated request while one is pending, a goal without handle is cancelled when the late acceptance arrives, a missing result keeps the existing `cancel_timeout`/RECONCILIATION_REQUIRED path). Atomicity: the run loop thread is the only writer of the contract fields and calls `_on_command` right after updating them, so the receipt check and the stamp cannot be separated by an invalidation; the ROS thread re-checks under the ROS lock immediately before `send_goal_async`. Residual: an invalidation that happens after that last check but before the stub/real Nav2 accepts the goal is covered only by the cancel duty (cancel is requested on the next monitor run, up to about 0.1 s; this period is not a stopping-time guarantee).
Redelivery of a rejected command re-sends the stored terminal result by the existing ACK-loss design (same status, no conflicting status): the tests check the status set, not the number of identical ACKs.

## 5. Agent v5 impact
Agent-only change (`core.py`, `ros_adapter.py`, `safety_protocol.py`), so it needs the v5 package and the isolated robot verification (not done). Wire format unchanged. A v5 Agent behaves as before with a valid server; with a contract-less server it now refuses motion at receipt, and a command received just before a contract flap is refused (`CONTRACT_GENERATION_CHANGED`) rather than executed; the server then sees a terminal REJECTED for that command.
